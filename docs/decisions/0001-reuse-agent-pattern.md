# 0001. stat-agent/realty-agent/air-agent 설계 원칙을 그대로 재사용한다

- 상태: 승인됨
- 날짜: 2026-10-19

## 배경

지원 중인 포지션의 주요 업무(기업·산업·재무 데이터 조사/분석, 투자검토·기업분석
업무 지원, LLM 프롬프트 작성)와 맞닿는 포트폴리오가 없었다. 기존에 만든 공공데이터
+ Claude tool-use 에이전트 3종(KOSIS 통계, 국토부 실거래가, 에어코리아/기상청)의
설계를 기업 재무 공시(DART) 도메인으로 확장하기로 했다.

## 결정

1. **3-tool 패턴 유지**: `resolve_company`(모호한 입력 해소) → `get_financials`
   (원자료 조회) → `compute_growth`(코드 계산)로, 기존 프로젝트들의
   "엔티티 resolve → 원자료 조회 → 코드 계산" 구조를 그대로 가져온다.
2. **출처 명시 원칙 유지**: 모든 숫자에 공시 접수번호(rcept_no)·사업연도·
   연결/개별 여부를 붙인다. 계정을 못 찾으면 null로 두고 모른다고 답하게 한다
   (지어내지 않는다).
3. **계산은 코드로, 모델은 암산 금지**: 증감률은 `compute_growth`에서만
   계산하고, 시스템 프롬프트에서 모델이 직접 계산한 숫자를 쓰지 않도록
   명시한다.
4. **고정 정답 eval 재사용**: DART 공시는 한 번 등록되면 바뀌지 않는
   "확정 데이터"이므로, stat-agent와 동일하게 과거 확정 사업연도 기준
   고정 정답셋으로 정확도를 측정한다 — realty-agent/air-agent처럼 매번
   바뀌는 데이터가 아니라서 eval 설계가 더 단순하다. (`eval/cases.json`의
   expected_amount는 실제 DART 공시를 직접 대조해 채워야 하며, 비워둔
   case는 eval 러너가 SKIP으로 표시한다 — 검증 안 된 숫자를 정답으로
   깔아두지 않기 위함이다.)

## 트레이드오프

- 기존 3개 프로젝트와 코드를 직접 공유하지 않고 설계만 재사용했다 (별도
  레포라 참고할 수 없었다). 계정과목 표기 변형 매칭 같은 이 도메인 고유의
  디테일은 이 프로젝트에서 새로 검증해야 한다.
- 시간이 촉박해 도구를 3개로 최소화했다. 상태 추적·SLA 같은 백엔드
  요소는 이번 범위에서 제외했다 (해당 패턴은 다른 프로젝트에서 다룬다).

## 알려진 리스크 (README 참고)

- 계정과목(`account_nm`) 표기가 업종/회사마다 달라 매칭이 실패할 수 있다.
- CFS(연결)→OFS(개별) 폴백 로직이 핵심이며, 자회사 없는 회사는 CFS 조회 시
  항상 013을 반환한다.
- "최근 사업연도"가 공시 시차 때문에 생각보다 과거일 수 있다 — KST 기준
  날짜 계산이 필요하다.
- 일일 API 호출 한도(020) — 개발 중 TTL 캐시 없이 반복 호출하면 금방
  소진될 수 있다.
